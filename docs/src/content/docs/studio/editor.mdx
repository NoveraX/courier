Studio knows how every call to each endpoint went; your editor knows where the code makes them. The Courier extension puts the two together, above the call itself, and the figures move as your app runs:

And the other way round, Studio's inspector and Explorer list the code that calls an endpoint, each call site opening in your editor at its line.

## Install

| Editor | Where |
| --- | --- |
| VS Code | **Courier Studio** in the Extensions view, or the [Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=noverax.courier-vscode) |
| Cursor, Windsurf, VSCodium | **Courier Studio** in the Extensions view, from [Open VSX](https://open-vsx.org/extension/noverax/courier-vscode) |

Or from a terminal:

```bash
code --install-extension noverax.courier-vscode
```

Then start Studio for your project — **Start Studio** in the Courier view or the status bar, or a terminal as you always do — and the extension finds it on its own:

```bash
npx @noverax/courier-studio
```

Courier installs [Courier File Icons](#courier-file-icons) with it, as its extension pack: the part that puts Courier's icons into your icon theme, which runs where the editor's window runs.

**Help → Welcome → Get Started with Courier** walks you through it: setting Courier up, starting Studio, reading the figures and giving your agent the API.

## What you see

Above each call to an endpoint, how that endpoint's calls went in this session: how many there were — and the requests they sent, where a read another call's request answered sent none — how many requests failed and how many calls are still in flight, and how long nineteen in twenty took. A stream or a channel counts its connections, how many are being opened again after the last one ended, and how many are still open. The figures come up to date every few seconds while the editor has focus, and a click on the line opens the endpoint in Studio's Explorer.

Hover over the call for the rest: the median and the 95th percentile, the statuses the calls ended with, and the latest failure with its reason. **Open in Studio** opens the endpoint; **Open the latest failure** opens that request in Studio's inspector — its variables, its response, its timing.

### At the end of the line instead

A line above each call costs a line of the screen per call. Set `courier.hints.style` to `inlay` and the same figures sit at the end of the call's own line, as an inlay hint: its tooltip holds the figures in full, and a click on it opens the endpoint in Studio. The editor's own **Editor › Inlay Hints: Enabled** setting must leave inlay hints on.

## Studio in your editor

Every page of Studio's the extension opens — an endpoint from its hint or the Courier view, a request from the Requests view, the audit from a finding — opens in a tab of the editor's own, beside your code, and the next one opens in the same tab without loading Studio again. **Courier: Open Studio in Editor** opens Studio there on its own; **Courier: Open Studio in Browser** opens your browser instead, and `courier.studio.openIn` set to `browser` sends every page there.

<Screenshot

The tab shows Studio in the editor's theme, light or dark, and follows it when you switch. It opens with your project's token, so what changes things in Studio — a scenario switched, a schema fixed, a mock declared — works there as in the page Studio's own link opens. **Called from**, in the tab, opens the file beside Studio at its line. The editor keeps the tab across restarts, open on the page it showed. In a remote workspace — over SSH, in a container — the tab reaches Studio through the port the editor forwards.

## From a call to its endpoint, and back

The editor reads the project's endpoints from Studio as it reads your code's own:

| Where | What it does |
| --- | --- |
| **Go to Definition** on a call | Opens the endpoint's declaration in its group's file — the method, the path, the response |
| **Find All References** on a call or a declaration | Lists every call to the endpoint the project's code makes |
| Above a declaration | The endpoint's figures, and how many places call it — a click lists them |
| **Go to Symbol in Workspace** | Every endpoint by its full name: `#orders.place` finds the declaration |

A hook that names its endpoint as a string, as `q.orders.useQuery("list")` does, goes to the same declaration. A declaration moved in a file you save is found again at once.

### Requests and mocks

Below the endpoints, two views follow the session as it runs. **Requests** lists the latest requests Studio recorded, newest first — the endpoint, its method, its status and how long it took — a failed one in the editor's colour for a failed test, and a click opens it in Studio's inspector. **Show Failed Requests Only**, in its title bar, keeps to the failures.

**Mocks** lists each mock server Studio runs, its address, and the delay and faults set on it; open one for its scenarios, the one in force marked, and click another to switch to it. **Delay Answers…** sets one of Studio's delays on a mock — 4G, 3G, satellite — **Fail Some Answers…** one of its fault presets — degraded, unstable, down — and **Stop Delays and Faults** takes both off again. They change the mock with your project's token, as Studio's own Mocks page does.

**Start Studio** runs your project's own `studio` script through the package manager its lockfile names, when that script runs Courier Studio, and `npx @noverax/courier-studio` otherwise — in a terminal of its own, named after the project. Asked again, it shows that terminal.

## Adding to your API

**Courier: New Endpoint…** — from the palette, the Courier view's menu, or the editor's context menu while Studio runs — asks which group, its name, its method and its path, and types the endpoint in after the group's last one, the way that file writes its endpoints: the same builder, the same indentation, a comma where one is needed. Its variables and its response are left for you to fill in, a <kbd>Tab</kbd> apart. With the cursor among a group's endpoints, that group is offered first; a name the group already has is refused as you type it.

| Command | What it does |
| --- | --- |
| **Courier: Import an API…** | Runs `courier-studio import` on an OpenAPI, Swagger or Postman document, from an address or a file of the project's. For an address behind auth it asks the kind — a bearer token, a user and a password, or headers — and the environment variables that hold them, and runs the command with their names alone: [Specifications behind auth](/docs/studio/import-access#specifications-behind-auth). An address with a user or a password in it is refused as you type it; one with a key in its query is taken with a warning, as the key goes onto the command line — when the host takes the key in a header too, pick Headers instead |
| **Courier: Show OpenAPI Document…** | Opens a source's OpenAPI document, as Studio writes it from your config, in an editor tab |
| **Courier: Check API Changes…** | Runs `courier-studio diff` against a branch, a tag or a commit, and reports what the change breaks |

Each runs in a terminal of its own, named after it and the project, in the project's folder, as `npx @noverax/courier-studio …` — the project's own Studio when it has one installed. The terminal starts the command itself, each argument whole, rather than typing a line into your shell: no shell reads an address you gave, PowerShell's `$(…)` and `cmd`'s `&` included, and none keeps the line in its history. Once the command ends, your shell takes the terminal over on macOS and Linux, and `cmd` on Windows.

## Tasks and tests

**Terminal › Run Task… › courier** lists Courier's commands for each project of the workspace: `studio` runs Studio in the background, `verify` checks every recorded call against the API as declared now, `openapi` writes each source's OpenAPI document into `openapi/`, `diff` reports what a change breaks against `origin/main`, and `agents` lists what the project offers agents and why. A task of your own names them in `tasks.json`:

```json
{
  "type": "courier",
  "command": "verify",
  "project": "apps/shop"
}
```

The calls Studio recorded as tests — the files under `tests/recorded/` — show in the **Test Explorer**, each file with its calls. Running them checks each call against the API as your code declares it now, through `courier-studio verify`: a call whose answer the declared schema no longer takes fails, with what changed and where.

## Ask @courier

In the editor's chat, `@courier` answers from the Studio of the file in front:

| Command | What it answers |
| --- | --- |
| `/status` | How every endpoint is doing: the ones with failed calls first, then the slowest, each with its figures |
| `/failures` | The latest failed requests and why, with a button to the newest in Studio's inspector |
| `/audit` | What the audit found in the requests, gravest first |
| `/endpoint` | One endpoint — named, or the one under the cursor — its figures and latest calls, linked to its declaration and the code that calls it |

Any other question — *why does checkout fail?* — goes to the model you picked in the chat, with Studio's figures for this session: how the endpoints are doing, the latest failures, the audit's findings, and the latest calls of each endpoint the question names. Each answer offers what to ask next. The chat needs a language model in the editor — GitHub Copilot's, or one an extension provides — and `@courier` shows only in a workspace with a Courier project or a running Studio.

## The audit at your calls

Studio's [audit](/docs/studio/audit) reads the requests it recorded; the extension marks its findings at the calls they concern, in the files you open and in the Problems panel under **Courier audit**: an N+1 pattern where the code asks for each item and where it lists them, a timeout risk at the slow endpoint's calls, a write retried without an idempotency key where the code writes.

An audit error is a warning in the editor — the code compiles; its traffic needs a look — an audit warning is information, and a hint a hint. Findings of one kind at one call make one mark, at the gravest of them. Each mark links to Studio's Audit page, where the finding reads in full with its fix.

## Told when a call fails

Set `courier.notifications.failures` and a call that fails while you work brings a notice — the endpoint and why, with the system's code and text when no answer came — with a button to the failure in Studio's inspector and one to the failed requests. Each endpoint is told of at most once a minute, several failing together share one notice, and the failures already there when you turn it on are not told again. It is off until you turn it on.

## Your API, for VS Code's agent

VS Code's agent finds Courier's [MCP servers](/docs/agents/editor) on its own — nothing to write in `.vscode/mcp.json`. Each project of the workspace offers the ones it has installed, each run from the project's folder, and started only when the agent first needs it:

| Server | Offered when the project has | What the agent gets |
| --- | --- | --- |
| **Courier API** | `@noverax/courier-mcp` | The endpoints marked `.agent()`, and those the [`agents` policy](/docs/agents/overview#what-agents-may-call) offers |
| **Courier Studio** | `@noverax/courier-studio` | The requests Studio recorded, its audit, its mocks and their scenarios |

The API's server is handed the project's `.env.development.local`, `.env.local`, `.env.development` and `.env` — those that exist, the first one setting a variable winning — so its calls reach your backend. It needs VS Code 1.101 or later; Cursor and Windsurf configure their agent's servers themselves, as [In Your Editor](/docs/agents/editor) shows.
