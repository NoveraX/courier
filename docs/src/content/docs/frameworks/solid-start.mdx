`@noverax/courier-solid` serves the proxy that `createProxyCaller` and `createProxyQueryCaller` call: one route answers every endpoint, reads over `GET` and writes over `POST`, and streams server-sent events.

## In one command

```bash
npx @noverax/create-courier
```

In a SolidStart app it adds what this page sets up by hand — the API route that registers your APIs, and Studio's plugin — with a typed example API, its mock, and a page at `/courier`. See [Create Courier](/docs/create-courier).

## Install

```bash
npm install @noverax/courier-solid @noverax/courier @solidjs/start
```

## Usage

```ts side="server"
// src/entry-server.tsx
import { registerSources } from "@noverax/courier/server"
import { sources } from "~/api"

registerSources(sources)
```

```ts
// src/routes/api/request.ts
import { courierHandler } from "@noverax/courier-solid"

const handler = courierHandler()
export const GET = handler
export const POST = handler
```

`courierHandler()` is zero-arg — sources are read at request time from the core global registry populated by `registerSources()` at server startup. The handler uses Web Standard `Request`/`Response` natively. A read that may be cached arrives as GET, and every other call as POST.

The proxy reads a JSON call up to its `maxBodyBytes`, 1 MB, and an upload (`multipart/form-data`) up to its `maxUploadBytes`, 10 MB; pass others to raise them: `courierHandler({ maxUploadBytes: 50 * 1024 * 1024 })`.

Solid Start renders the page for a method the route does not export, so `PUT`, `DELETE` or `OPTIONS` on `/api/request` answer 200 with HTML rather than an error. Courier clients send only `GET` and `POST`; export the handler for the other methods too if anything else may call the route, and the proxy answers them with 405. In development, the dev server turns an upstream's `205 Reset Content` into a 500.

## The client

Courier's plugin gives the page its routes, built from the endpoints you mark `.expose()`. It runs on `@noverax/courier-build`, which only the build needs:

```bash
npm install --save-dev @noverax/courier-build
```

```ts title="vite.config.ts"
import { solidStart } from "@solidjs/start/config"
import { courierRoutes } from "@noverax/courier-solid/plugin"
import { defineConfig } from "vite"

export default defineConfig({ plugins: [solidStart(), courierRoutes()] })
```

SolidStart 1 takes it in `app.config.ts`, as `defineConfig({ vite: { plugins: [courierRoutes()] } })`.

Pair with `createProxyCaller` on the client, given those routes, in a module that registers the config, so they are typed from it — see [Exposing Endpoints](/docs/proxy-mode/expose):

```ts title="src/caller.ts" side="page"
import { createProxyCaller } from "@noverax/courier/client"
import { routes } from "@noverax/courier/routes"

import type config from "../courier.config"

declare module "@noverax/courier/routes" {
  interface Register {
    config: typeof config
  }
}

// The routes name the key this source has in your `sources` map —
// it is what the proxy addresses, and it travels as `?_s=<name>`.
export const caller = createProxyCaller(routes.api, {
  proxyPath: { http: "/api/request" },
})
```

A project that takes `courier.routes.ts` moves to the plugin with `npx @noverax/courier-cli setup`; one that would keep the file writes it with `npx @noverax/courier-cli routes`, and gives the caller `apiRoutes` from it in place of `routes.api`.

## The user's session

An API that keeps a `session` gets the user's session with every call a page's `query`, a server function, an action, an API route or a step it awaits makes. SolidStart keeps the request it is serving itself; register its `getRequestEvent` once, in the server entry:

```tsx title="src/entry-server.tsx" side="server"
import { registerRequestContext } from "@noverax/courier/server"
import { solidStartRequestContext } from "@noverax/courier-solid"
import { getRequestEvent } from "solid-js/web"

registerRequestContext(solidStartRequestContext(getRequestEvent))
```

The session cookies the API sets reach the browser on the response SolidStart prepares: a page's, a server function's, an API route's, and an error response's too. A page streams, and its headers leave with its first part: a cookie the API sets after that cannot reach the browser, and the log says so. Load what may renew the session with `deferStream: true`, so the page waits for it:

```tsx title="src/routes/account.tsx"
const getMe = query(me, "me")

export default function Account() {
  const user = createAsync(() => getMe(), { deferStream: true })
  // …
}
```

The calls the same request makes after it still send the renewed session; only the browser keeps the old one. `forward`'s client address is the one SolidStart reports for the request.

SolidStart 1 and 2 are checked with the Node server their build makes. See [User Sessions](/docs/server-side/session).

## Cancelled calls

When the browser cancels a call — an aborted upload, a query it no longer needs — the proxy stops its own upstream request. The dev server builds the request without a signal that reports a client leaving, so the handler watches the Node response on the event's `nativeEvent` as well, in development and in production alike.
