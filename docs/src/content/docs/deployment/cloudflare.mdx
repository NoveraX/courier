## Overview

Cloudflare Workers run at the edge with specific constraints for long-lived connections:

| Feature | Support | Limit |
|---------|---------|-------|
| HTTP | Full | Standard request limits |
| SSE | Supported | **100 second idle timeout** |
| WebSocket | Not in a Worker | A Node.js server, or a Durable Object you bridge |

## SSE on Workers

Courier SSE works on Workers because it uses the Web Standard `fetch` + `ReadableStream` API — no Node.js dependencies.

### Hono on Workers

```ts title="src/index.ts" side="server"
import { Hono } from "hono"
import { registerSources } from "@noverax/courier/server"
import { courierHandler, courierSSEHandler } from "@noverax/courier-hono"
import { sources } from "./api/sources"

registerSources(sources)

const app = new Hono()

app.all("/api/request", courierHandler())

app.get("/api/sse", courierSSEHandler({
  sseMaxLifetimeMs: 90_000,      // close before 100s idle timeout
  sseHeaders: {
    "Access-Control-Allow-Origin": "https://app.example.com",
  },
}))

app.get("/health", (c) => c.json({ status: "ok" }))

export default app
```

### Heartbeat Configuration

Cloudflare terminates connections after **100 seconds of inactivity**. The Courier SSE server sends heartbeat pings every 25 seconds by default, which keeps the connection alive.

```text title="Heartbeat timeline"
Timeline: 0s ───── 25s (ping) ───── 50s (ping) ───── 75s (ping) ───── 100s limit
                ↑ alive          ↑ alive          ↑ alive          ↑ reset
```

<Callout variant="tip" title="Default heartbeat is sufficient">
  The built-in 25-second heartbeat interval is well within Cloudflare's 100-second timeout. No additional configuration needed.
</Callout>

### Max Lifetime

Even with heartbeats, set `sseMaxLifetimeMs` to force periodic reconnection. This prevents zombie connections and ensures clean resource rotation:

```ts
courierSSEHandler({
  sseMaxLifetimeMs: 300_000,  // reconnect every 5 minutes
})
```

The client reconnects with `Last-Event-ID`, which the proxy sends upstream: a backend that resumes after it loses no events.

## WebSocket on Workers

A Worker accepts WebSocket connections, but Courier's sockets do not run in one. `upgradeWebSocket` from `hono/cloudflare-workers` never calls `onOpen`, where `courierWSHandler` takes a connection up, so the connection opens and nothing answers it. And a Worker serves each connection in its own request, which cannot reach a socket another request opened: a topic's broadcast needs every connection of the topic in one place.

### Option A: Separate WS Server (Recommended)

Run WebSocket on a separate Node.js server and keep Workers for HTTP + SSE:

```
Workers (Edge):     HTTP proxy + SSE streaming
Node.js Server:     WebSocket (via @noverax/courier-server)
```

This gives you the best of both — edge latency for SSE, full WS support on a dedicated server.

### Option B: Durable Objects

<Callout variant="warning" title="Advanced setup">
  A Durable Object keeps the connections it accepts in one place, on the Workers Free plan too with SQLite storage. It is not a Courier adapter: you bridge the Durable Object WebSocket API to Courier manually.
</Callout>

```ts title="src/durable-object.ts"
import { DurableObject } from "cloudflare:workers"

export class CourierWSObject extends DurableObject {
  async fetch(request: Request): Promise<Response> {
    const upgradeHeader = request.headers.get("Upgrade")
    if (upgradeHeader !== "websocket") {
      return new Response("Expected WebSocket", { status: 426 })
    }

    const pair = new WebSocketPair()
    const [client, server] = Object.values(pair)
    this.ctx.acceptWebSocket(server)

    return new Response(null, { status: 101, webSocket: client })
  }

  async webSocketMessage(ws: WebSocket, message: string | ArrayBuffer): Promise<void> {
    // Bridge to Courier WS protocol here
  }

  async webSocketClose(ws: WebSocket, code: number): Promise<void> {
    // Cleanup
  }
}
```

## Limitations

| Limitation | Impact | Workaround |
|-----------|--------|------------|
| 100s idle timeout | SSE must keep-alive | Built-in heartbeat (25s) handles this |
| Courier's sockets do not run in a Worker | `courierWSHandler` never takes a connection up | A Node.js server, or a Durable Object you bridge |
| Studio's runtime attaches nothing | Studio sees none of the Worker's calls, and its Playground has no proxy mode for it | Serve the routes on Node.js in development — see [Hono](/docs/frameworks/hono#studio-app-origin) |
| No persistent connections across deploys | Connections drop on new deployment | Client auto-reconnects via `Last-Event-ID` |
| CPU time limits (10ms free / 30s paid) | Long SSE generators may hit limits | Keep event generation lightweight |
| No `node:http` module | Express/Fastify won't work | Use Hono (Web Standard APIs) |

## Multi-Region

Cloudflare Workers run in 300+ data centers automatically. No replica configuration needed — Workers scale horizontally by design.

For shared state across regions, use:
- **Cloudflare KV** — eventually consistent key-value store
- **Durable Objects** — strongly consistent, single-region per object
- **External Redis** (Upstash) — serverless Redis with global replication

```ts title="src/index.ts"
import { createRedisPubSub, createRedisStream } from "@noverax/courier-redis"
import { Redis } from "@upstash/redis"

// Upstash Redis works in Workers (HTTP-based, not TCP)
// Note: requires @upstash/redis, not ioredis
```

<Callout variant="warning" title="ioredis compatibility">
  `ioredis` uses TCP connections and does **not** work in Cloudflare Workers. Use [Upstash Redis](https://upstash.com/) with its HTTP-based client, or connect to Redis from a separate Node.js server.
</Callout>
