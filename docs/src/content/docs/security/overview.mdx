## What Courier secures, and what it leaves to your API

Courier carries calls from your application to your APIs. Deciding who a user is and what they may do stays with the API: Courier sends the credentials a call needs, to the API it is meant for, and nothing else, anywhere else. Along the way it refuses the calls another site sets off, keeps one user's answers away from another, and keeps credentials out of its logs, its caches and Studio.

This page follows the user's credentials through each layer. [User Sessions](/docs/server-side/session) describes how a session is set up, and [Server Handler](/docs/proxy-mode/api-route) how the proxy route is mounted.

## Where credentials travel

| Where the call starts | What holds the user's credentials | What Courier sends to the API | What it never sends |
| --- | --- | --- | --- |
| A page, calling the API directly | The browser's own cookies, which it sends itself as far as its rules let it | The double-submit token a page can read, repeated on writes | — the browser decides the rest |
| A page, through your proxy route | The cookies and headers the browser sends to your application | `Referer`, `Origin`, `Authorization` with a token your scripts set, `User-Agent`, `X-Request-Id`, the headers `allowedHeaders` or `.headers()` name, the session's cookies, and `X-Forwarded-For` the proxy writes from the connection and the chain the proxies in front recorded | Your application's other cookies, `Authorization` in `Basic`, `Digest`, `Negotiate` or `NTLM`, and every header that claims a client address |
| Your server, while it serves a request — a page, a Server Action, a route | The request being served | The cookies `session.cookies` names, `Authorization: Bearer` from the `bearer` cookie, the double-submit header on writes, `Referer` with your origin, and the headers `forward` names | Everything else the request carries |
| A React Native app | The platform's cookie store, and the readable cookies Courier keeps from the API's answers | The double-submit token Courier kept, repeated on writes | — the platform sends its own cookies |
| A stream (SSE) | As for a call from the same place | The same, again on every reconnect | The same |
| A channel (WebSocket) | As for a call from the same place | On Node and React Native, headers on the handshake; from a browser, the first frame on the socket | Credentials in the address |

### The proxy serves only what you mark

A page reaches an endpoint through the proxy only where a mark opens it — `.expose()` on the endpoint, or `expose` on its group or its API — and any other is answered as a name the source does not define. A page's client learns the routes alone, nothing of the API's definition. See [Exposing Endpoints](/docs/proxy-mode/expose).

### The proxy passes on only what it names

The proxy forwards the browser's headers on a short list and those named in `allowedHeaders` or `.headers()`. The rest stay behind: the browser's cookies, which would reach whatever upstream a source points at, but those an API's `session` names; the logins a browser sends by itself to your own site; and the headers that claim a client address. A header your server sets is the one the API receives, whatever the page wrote, and the API's cookies come back on a path of their own, described below. See [Header whitelisting](/docs/proxy-mode/overview#header-whitelisting) and [Cookies](/docs/proxy-mode/api-route#cookies).

### Only to the API's origin

A call that carries the user's credentials from a server follows a redirect only while it stays on the API's origin; a redirect anywhere else is answered with as it came, an upload's included. A session goes over plain HTTP only to the local machine or a private network, unless it sets `allowHttp`. The address `csrf.from` names is a path on the API's own origin, and an endpoint's path always stays under its API's `baseURL`.

### Streams and channels

A stream carries the session as a call from the same place does, read again on every reconnect. A browser cannot put headers on a WebSocket handshake, so a Courier client sends what proves who it is in the socket's first frame, never in the address, where it would reach access logs and browser history. Through the proxy, the upstream socket is opened for each user with that user's session, never shared between users. See [Streams and channels](/docs/server-side/session#streams-and-channels) and [Who a connection is](/docs/advanced/realtime-connections#who-a-connection-is).

### React Native

A React Native app keeps its cookies where no script reads them, and sends them to every call to their host whether the API describes a session or not. The cookies a page could read — the double-submit token, a bearer token — Courier keeps from the answers of its own calls, for the host, domain and path they were set for, and a `Domain` of one label, such as `com`, is not taken. See [The user's session](/docs/frameworks/react-native#the-users-session).

## What reaches the browser

An API's answer can renew the session, hand out a double-submit token, or sign the user out. On a server, Courier carries those cookies on — to the calls still to be made for the same request, and to the user's browser on your application's response — and only the cookies the session names, the double-submit cookie and the bearer cookie; any other cookie stays with the API. Each is made for your application's origin, for every path and `Secure` only where it can be, and `session.relay: false` keeps even the session's own cookies within the request. The rules, and where each framework can and cannot set a cookie, are in [The cookies the API sets](/docs/server-side/session#the-cookies-the-api-sets).

## Requests another site sets off

A page on another site can make the user's browser send your application a request, with the user's cookies on it. Courier refuses such a request wherever it would act for the user.

### The proxy's origin rule

Every call the proxy serves — GET, POST, a stream and a channel — is checked for where it comes from. `Sec-Fetch-Site` decides wherever the browser sends it, and `Origin` where it says nothing else: a page of your application's passes, a page of another site only from an origin in `allowedOrigins`, and a request with neither header, which no browser made, is served. `allowedHosts` names the hosts your application answers to, so a name an attacker points at a developer's server — DNS rebinding — is answered `421`. A list that cannot be read closes the application rather than opening it. The rules, the patterns a list takes and what each admits are in [Origin validation](/docs/proxy-mode/overview#origin-validation) and [Host validation](/docs/proxy-mode/overview#host-validation).

A GET to the proxy reaches only an endpoint that reads, and the variables of an endpoint marked `sensitiveVariables` are refused in an address: such a call goes as POST.

### Writes made with the user's session

Your server makes calls with the user's session while it serves a request, and a write made then acts for the user. It is made only when the request being served is one of your application's own — a form, a Server Action or a `fetch` that passes the origin rule above, or a page the browser marks as your application's or as opened by the user. Anything else is refused with `403` before it reaches the API, and the log and Studio say why. A sign-in is guarded too, a write that does no harm when a stranger sets it off says so with `session: "unguarded"`, and a read sent over POST is a read here. See [Writes another site sets off](/docs/server-side/session#writes-another-site-sets-off).

### Channels

A channel's socket passes the origin rule as it opens, so a page on another site cannot open one with the user's cookies. Its first frame may add the headers a browser could not put on the handshake, and never those a browser or a proxy sets — see [Who a connection is](/docs/advanced/realtime-connections#who-a-connection-is).

## AI agents

An endpoint reaches an agent only when it is marked `.agent()` or the project's `agents` policy offers it, and then as an MCP tool whose call runs through the endpoint's middleware and schemas like any other — see [MCP Server](/docs/agents/overview).

- **Nothing offered by default.** The policy lives in `courier.config.ts`, under review, and a server's start can narrow it, never widen it — see [What agents may call](/docs/agents/overview#what-agents-may-call).
- **No browser session.** An agent's call carries none of the request it arrived on, and runs with what your middleware gives the principal `authorize` let in.
- **Callers you authorize.** `createMcpHandler` cannot be created without `authorize`, and `allow` keeps a tool from a caller as if it did not exist — see [In Your App](/docs/agents/app#who-may-call).
- **Limits and confirmations.** A tool's limit refuses a call beyond it before anything runs, and a person confirms what cannot be undone, out of the model's reach — see [How often an agent may call](/docs/agents/overview#how-often-an-agent-may-call) and [A person confirms](/docs/agents/overview#a-person-confirms-what-cannot-be-undone).
- **What reaches the model** is an answer, or an error cut short and cut of its credentials, never a response header — see [How a call runs](/docs/agents/overview#how-a-call-runs).
- **What Studio keeps.** An agent's calls show with the tool and the client. Studio's own MCP endpoint answers only with Studio's token, hands an agent no credential, and sends a recorded write again only once the person confirms it — see [Studio for Your Agent](/docs/agents/studio#what-it-shows-and-to-whom).

## Webhooks

A webhook is a call made to your app by its sender, and [`defineWebhook`](/docs/advanced/webhooks) checks each delivery before your handler sees it: its size as it arrives, its signature over the body exactly as it came, its age where the scheme signs one, and its body against the webhook's schema. A webhook without a secret refuses every delivery rather than take an unsigned one, and Studio can have a delivery sent to your app, which the app signs, so the secret stays where it is. See [What a delivery passes](/docs/advanced/webhooks#what-a-delivery-passes).

## Caches

`cacheMiddleware({ scope: "public" })` never stores or serves an answer to a call that carries a session. `scope: "session"` keeps one partition per set of credentials a call sends, named by their SHA-256 digest so that no credential sits in a cache key, a Redis keyspace or a log line. See [the cache middleware](/docs/middleware/built-in#cachemiddleware).

## What Courier writes down

- **Its log.** An `HTTPError` carries the API's answer whole. Printed — by Courier's log, `console.error`, or Node's report of an uncaught error — it shows every header with each credential's value hidden, by the rules of [`redact()`](/docs/api/redact), and `error.headers` still holds them all for the code that reads them. Courier's server log loses every credential first — see [Logs](/docs/deployment/overview#logs) — and `COURIER_LOG_FORMAT=json` prints an error's name, message, code and status alone. `logMiddleware` logs a failed call's status, never the answer it carried, and a warning about something a client sent names it by what the server knows, never in the client's own words.
- **An upload's files.** Under Node the proxy writes what an upload holds past `uploadMemoryBytes` to disk while its call runs, in a folder of the call's own that only the server's user may read, and removes it once the call has its answer — see [where the proxy keeps an upload](/docs/proxy-mode/uploads#where-the-proxy-keeps-an-upload).
- **Studio.** Studio keeps what it captured in `.courier/studio.db`, readable by your account alone, with every credential header's value written as `[redacted]`. An error's text, its cause and a request's address leave the page that holds Studio's token — written down, exported, told to an agent or shown to a page without the token — with their credentials cut; see [No credential is kept](/docs/studio/storage#no-credential-is-kept). Studio makes changes only for a page opened with the token in `.courier/studio-token` — see [Start Studio](/docs/studio/overview#start-studio). A [session file](/docs/studio/session-files) shared for a bug report carries no credential either, and to follow [contract drift](/docs/studio/contract-drift) Studio keeps the shape of each answer, never a value.

## Limits at the edge

| What | Default | Option |
| --- | --- | --- |
| Calls from one caller through the proxy | None — set one | `rateLimit` |
| Requests no browser sent, Studio's Playground in development aside | Served | `browsersOnly` |
| A JSON body to the proxy | 1 MB | `maxBodyBytes` |
| An upload to the proxy | 10 MB | `maxUploadBytes` |
| Fields and files in one upload | 1000 | `maxUploadParts` |
| What every upload keeps in memory at once | 64 MB | `totalUploadMemoryBytes` |
| What every upload keeps on disk at once | 1 GB | `totalUploadDiskBytes` |
| An upload's text fields, together | 1 MB | `maxBodyBytes` |
| A pause between two pieces of a request body | 30 seconds, then `408` | `bodyIdleTimeoutMs` |
| A request body's whole arrival | 5 minutes, then `408` | `bodyTimeoutMs` |
| A stream's lifetime | 30 minutes | `sseMaxLifetimeMs` |
| A WebSocket message | 64 KB | `maxMessageSize` |
| Connections from one address | 50 | `maxConnectionsPerIP` |
| Messages per connection | 100 a second | `maxMessagesPerSecond` |
| Subscriptions per connection | 100 | `maxSubscriptionsPerConnection` |
| Wait for a channel's first frame | 3 seconds | `authTimeoutMs` |

Subscribing, leaving and re-authenticating are counted apart from other messages, so a flood of messages cannot hold back an unsubscribe. A request the server cannot read — an upgrade whose address or `Host` no URL can name, a frame that is not one a client sends — is answered or closed on its own, and a failure while one connection is served ends that connection, never the process the others live in.

## Development and production

| | Development | Production |
| --- | --- | --- |
| A page on another local port | Admitted while `allowedOrigins` is empty and the app is served locally, so Studio can drive it — see [Origin validation](/docs/proxy-mode/api-route#origin-validation) | Never |
| Hosts answered while `allowedHosts` is empty | The local machine's names and IP addresses | Every name |
| The app's origin, for Studio's Playground | Taken, when not configured, from a request whose own `Host` is `localhost`, `127.0.0.1` or `[::1]` on the port the server accepted it on, sent from this machine, as far as the framework tells — see [`appOrigin`](/docs/api/config) | Never taken from a request |
| Studio's Playground under `browsersOnly` | Let through on a one-time pass only Studio's runtime in the process serving the route redeems — see [Studio's Playground](/docs/proxy-mode/rate-limits#studios-playground) | Refused, as a script is: no pass is honoured |

Courier counts as in development wherever `NODE_ENV` is not `production`, so set it on every server you deploy, a custom Node server included. It reads each variable of its own — `NODE_ENV`, `COURIER_ALLOWED_ORIGINS`, `COURIER_ALLOWED_HOSTS`, `COURIER_TRUSTED_PROXIES` among them — as the environment's own: Node looks a name the environment does not have up on `Object.prototype`, and a variable code elsewhere in the process put there leaves the setting unset. A `NODE_ENV` your bundler writes into the build is read as written.

## In production

- Set `NODE_ENV=production`.
- Reach your APIs over HTTPS, and leave `allowHttp` unset. Trust an internal certificate authority with `NODE_EXTRA_CA_CERTS` or an API's own `dispatcher`, never by turning the certificate check off — see [Proxies & Certificates](/docs/advanced/proxies-and-certificates).
- Name the session's cookies exactly, and a prefix only where every cookie under it belongs to the session.
- List in `allowedOrigins` only pages you serve, and in `allowedHosts` the names your application answers to — in the code, or in `COURIER_ALLOWED_ORIGINS` and `COURIER_ALLOWED_HOSTS` where it runs.
- Mark `session: "unguarded"` only on writes that do no harm when a stranger sets them off, and never declare a write `.reads()`.
- Forward the client's address only behind a proxy on the local machine or a private network.
- Print the log as JSON wherever it leaves the machine, with `COURIER_LOG_FORMAT=json`.
- Keep Studio on your own machine: it is a development tool, and its port is never one to expose.
- Give an MCP endpoint an `authorize` that identifies each caller, a `confirmSecret` shared by its replicas, and offer `.agent()` only on endpoints you would hand to an agent.

## Reporting a vulnerability

Report a security issue privately through GitHub's vulnerability reporting on the repository — never in a public issue. What is in scope, and how quickly you will hear back, is in `SECURITY.md`.
