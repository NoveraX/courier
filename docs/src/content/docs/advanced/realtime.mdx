## Overview

A `stream` delivers server-sent events; a `channel` is a WebSocket subscription, which the caller can also send on when it names `.send()`. Either one is served by the process that defines it with `.implement()`, or describes where another process serves it with `.get()`, `.connect()` or `.via()`.

```ts title="api/chat.ts"
import { courier, defineGroup } from "@noverax/courier/define"
import { z } from "zod"

const { channel } = courier()

export const chat = defineGroup({
  prefix: "chat",
  endpoints: {
    room: channel
      .variables(z.object({ room: z.string(), nick: z.string() }))
      .topic((v) => ({ room: v.room }))
      .send(z.object({ text: z.string() }))
      .response(z.object({ from: z.string(), text: z.string() }))
      .implement((v) => ({
        onJoin(ctx) {
          ctx.send({ from: "server", text: `welcome to ${v.room}` })
        },
        onMessage(ctx, message) {
          ctx.broadcast(ctx.topic, { from: v.nick, text: message.text })
        },
      })),
  },
})
```

## Serving a stream

A stream's `.implement()` takes an async generator, handed the subscription's `variables`, a `signal` that aborts when the client leaves, the `lastEventId` a reconnecting client resumes after, and the request's `headers`. Each event it yields is `{ data }`, with an `event` name or an `id` where it needs them; `tracked(id, data)` gives the event an id, so a client that reconnects is handed only what it missed:

```ts title="api/orders.ts"
import { courier, defineGroup } from "@noverax/courier/define"
import { ForbiddenError } from "@noverax/courier/realtime"
import { tracked } from "@noverax/courier/realtime"
import { z } from "zod"

const { stream, channel } = courier()

export const orders = defineGroup({
  prefix: "orders",
  endpoints: {
    updates: stream
      .variables(z.object({ shop: z.string() }))
      .response(z.object({ id: z.string(), state: z.string() }))
      .implement(async function* (ctx) {
        if (!(await canWatch(ctx.headers, ctx.variables.shop))) {
          throw new ForbiddenError("Not a member of this shop")
        }
        for await (const order of orderChanges(ctx.variables.shop, ctx.lastEventId, ctx.signal)) {
          yield tracked(order.id, order)
        }
      }),
    // A channel nobody sends on is served the same way; it yields the values themselves
    ticker: channel.response(z.number()).implement(async function* () {
      yield 1
    }),
  },
})
```

Returning ends the stream: the client stops reading and does not reconnect. Throwing fails it. A `RealtimeError` — `ForbiddenError`, `AuthError`, `RateLimitError`, `RealtimeTimeoutError`, or one built with its own code — reaches the client with its code and message; any other error reaches it as code `5000`, "Stream failed", and in full only the server's log.

## Reaching a stream or a channel

A stream or channel served with `.implement()` is reached through the server that serves it — the proxy routes of your framework adapter, or a [standalone server](/docs/deployment/standalone-server) — so a proxy caller opens it: `createProxyCaller`, or `createProxyQueryCaller` for the React hooks.

A stream is opened by asking for it, so through the proxy its variables travel in the address of the stream route — `/api/sse?_s=api&_g=live&_m=feed&_v={…}` — and every access log on the way writes them down. Keep what must not be written down, such as an email address, out of a stream's variables: the user's [session](/docs/server-side/session#streams-and-channels) carries who they are, and a header the source forwards carries the rest. A channel sends its variables in its subscription's first frame on the socket, never in an address.

A direct caller, `createCaller` or `createQueryCaller`, sends everything to the API's `baseURL`, which is the upstream's address. Nothing serves this process's streams and channels there, so calling one through a direct caller throws `ConfigurationError("DIRECT_CALL_TO_SERVED_ENDPOINT")`, naming it, when it is called — the React hooks report it through `error` — and the rest of the API stays callable. A stream or channel addressed with `.get()`, `.connect()` or `.via()` is another process's, and a direct caller opens it at `baseURL`.

A proxy caller reaches another process's stream or channel too: the proxy relays it, opening it where its definition says. A stream is opened with the source's `headers`, the request headers the proxy lets through, the user's [session](/docs/server-side/session#streams-and-channels), and whatever the source's middleware sets. A browser reaches a third party's stream through its own server, with no CORS to configure and no key of its own to hold. A channel's upstream socket is opened with the same headers, as a direct caller in the server's process would open it; the subscriptions relayed with the same headers share it, so one user's channels share a socket and no two users' do. The proxy relays the streams and channels it would forward as endpoints: one no `.expose()` mark opens stays unreachable.

- A stream's events pass on as they came: ids, event names, and data that is not JSON as its text. A dropped upstream connection is reopened from the last event id, while the client's stays open. The client's `Last-Event-ID` is sent upstream when it resumes.
- The stream ends as the upstream's ends. It fails as the upstream's fails: a refusal carries the upstream's status as code `4000 + status`, so a `401` arrives as `4401`. A client that leaves closes the upstream stream.
- A channel's frames pass both ways, and it ends as its upstream subscription ends, with its code — a connection the upstream refuses included. A message the upstream subscription has no room to hold, while it joins or comes back, is answered with a `4429` error on the channel, which goes on. Subscribers of the server with equal variables share one upstream subscription.
- A path parameter that is empty, `.` or `..` is refused before anything is sent, as it is for an HTTP call. Otherwise it would reach a route above the declared one with the server's credentials.

A channel or a stream is kept from clients until something marks it, as an HTTP endpoint is — `.expose()` on it, or `expose` on its group or its API — whether the server relays it or serves it itself with `.implement()`. A subscription to one nothing marks is answered as for a channel that does not exist (`complete` with `4403`), and a stream as for an unknown one (`400`), so a client guessing names learns nothing. While developing, the server's log says which endpoint it refused and why, once for each.

## Reading a subscription

Calling a stream, a push channel or a channel with `.send()` returns a subscription, and every kind reads the same way. A channel with `.send()` is the same object with `send` on it as well; on the others `send` does not exist, in the types or at run time.

```ts
const ticks = client.prices.ticks({ symbol: "ACME" }) // a stream or a push channel
ticks.on("data", (tick) => render(tick))

const room = client.chat.room({ room: "general", nick: "ada" }) // a channel with .send()
room.on("data", (message) => append(message))
room.send({ text: "hello" })
```

`for await` reads it too: each event comes with its data and, from a stream, its `id` and `event` name. The loop ends as the subscription ends, and leaving it early closes the subscription:

```ts
for await (const event of client.orders.updates({ shop: "north" })) {
  render(event.data)
}
```

What arrives before anything reads it — between the call and the first listener, or the loop — is kept for the first reader, up to a thousand events; past that the oldest are dropped, and `dropped` counts them. Once a listener reads, nothing is kept for later.

A subscription has five events. Listening to any other is a type error, and throws `ConfigurationError` `UNKNOWN_EVENT`.

| Event | Hears | Each time |
| --- | --- | --- |
| `data` | the data, and the event it came in | it delivers something |
| `error` | a `RealtimeError` | the server refuses a message, a handler fails or a message is dropped from a full queue — the subscription goes on — and once more when it ends with an error |
| `status` | `connecting`, `connected`, `reconnecting` or `disconnected` | its status changes |
| `open` | `{ first, resumed }` | it is open: the first time, again after each reconnect, and when the server says what it holds may be stale |
| `close` | `{ reason }`: `closed`, `completed`, or `failed` with its `error` | it ends |

A subscription is `connecting` from the moment it is made, and `connected` once the server runs it: a channel once the server has confirmed its subscription, not as soon as its socket opens. A listener that throws is logged, and the others still hear the event.

A channel or a push subscription made again after a drop tells the server the last event of its topic it counted, and `resumed: true` says the server sent every event it missed — the server keeps them for that only where the channel's handler has a `history`, or the server a Redis log: nothing needs reading again. `open` with `first: false` and `resumed: false` means what it missed may not have been sent — the server could not, or the topic's sequence broke while it ran: read what it shows again. A stream hears `resumed: false` after every reconnect.

`reconnect()` connects again at once. On a subscription that is open or waiting to reconnect, the socket or the stream's connection is opened anew, with its credentials asked for again; the channels of one caller share a socket, so all of them reconnect. A subscription the server ended opens again, its listeners kept — a loop that ended does not resume, a new one reads it. One the application closed stays closed: call the endpoint again. `close()` ends it for good.

## How a subscription ends

A subscription ends in one of three ways, and the client can tell them apart.

- **The client closes it** — `close()`, a loop left early, or a React hook unmounting. `close` says `closed`.
- **The server finishes it** — a stream's generator returned, or a channel closed itself. A loop leaves; `close` says `completed`. It does not reconnect.
- **The server fails it** — the handler threw, the subscription or the join was refused, its variables failed their schema, or a limit was reached. The `error` event hears the `RealtimeError` with the code and message the server sent, the status becomes `disconnected`, and `close` says `failed`; a loop rejects with the same error. A stream refused with a status no retry would change — a `4xx` other than `408` and `429`, or a redirect it does not follow, as one to another origin — arrives as code `4000 + status`, so a `401` is `4401` and a `302` is `4302`, and is not reconnected — a `401` aside, which is tried once more when the credentials asked for anew have changed; a `408`, a `429` and a `5xx` are retried as a dropped connection is, no sooner than the `Retry-After` the server sent.

A dropped connection is none of these: the client reconnects, resumes a stream after the last event id it saw, and subscribes its channels again — see [Staying connected](#staying-connected). When it has spent its retries, it fails with a `ConnectionError`.

```ts
import { isRealtimeError } from "@noverax/courier/realtime"

const updates = client.orders.updates({ shop: "north" })
try {
  for await (const event of updates) render(event.data)
  // the server finished the stream
} catch (error) {
  if (isRealtimeError(error) && error.code === 4403) showNoAccess(error.message)
  else throw error
}

const room = client.chat.room({ room: "general", nick: "ada" })
room.on("error", (error) => notify(error.message)) // a refused message: the channel goes on
room.on("status", (status) => setOnline(status === "connected"))
room.on("close", (info) => {
  if (info.reason === "failed" && info.error.code === 4401) signInAgain().then(() => room.reconnect())
})
```

A channel's `error` event also reports what it refused without ending: a message that failed its schema (`4422`), one larger than the server accepts (`4413`), or an `onMessage` that threw. `send()` returns whether the message went out or waits for the channel; `false` means it was dropped, with a warning.

## Topics

Every subscription to a channel is on a topic: the endpoint, `source.group.method`, qualified by a key. `ctx.topic` is the subscriber's own, and `ctx.broadcast(topic, data)` sends to every other subscriber on it — every replica's, with a [`pubsub` adapter](/docs/deployment/redis).

Without `.topic()`, the key is all of a subscriber's variables: subscribers share a topic only when their variables are equal. That is the safe default for a feed whose variables pick what it shows, but it splits a room into as many topics as it has members as soon as a variable belongs to one member — a nickname, a cursor colour.

`.topic()` names what subscribers share a topic by. It reads the variables as the schema produced them, and returns what JSON can carry. In the channel above, everyone in room `r1` is on one topic, so a broadcast reaches all of them, while each keeps its own `nick` in `v` and `ctx.variables`. A key that throws ends that subscription with code `5000`.

On one connection, subscriptions whose key is equal are one subscription: the newer subscribe replaces the older, whose `onLeave` runs, and both of the client's channels receive what is sent on the topic. Two browsers, or two tabs, are two connections.

`.topic()` is named before `.implement()`. A channel another process serves has its topics decided there, so naming it before `.connect()` or `.via()` throws `ConfigurationError("TOPIC_ON_REMOTE_CHANNEL")`.

<Callout variant="info" title="How a topic reads">
  The key is canonical JSON — `api.chat.room#{"room":"r1"}` — so every distinct key is a topic of its own. `qualifyTopic` from `@noverax/courier/realtime` builds a topic for `broadcastToTopic` on the server's connection registry.
</Callout>

## What a channel sends

A stream's events, a push channel's values and what a channel's handlers pass to `ctx.send()` and `ctx.broadcast()` are held to the endpoint's `.response()` schema before they leave the server, and the client receives the schema's output — defaults filled in, transforms applied. A channel's `ctx.send()` or `ctx.broadcast()` of a value that does not match throws a `RealtimeValidationError` where it was called and sends nothing; a channel's response schema must validate synchronously. [Validation](/docs/validation/standard-schema#channels) has the details.

## Message size

A server accepts messages up to its `maxMessageSize`, 64 KB by default, and answers a larger one with a `4413` error on a connection that stays open. The client does not send one: the server names its `maxMessageSize` when it admits the socket, and a channel's `send` of a message whose encoded frame is longer — longer than 64 KB, until a server has named its own — puts nothing on the wire: `send` answers `false`, and the channel's `error` event reads code `4413`. The channel and everything else on the socket go on.

A server whose WebSocket layer closes the socket over a frame too large to read, with close code `1009`, loses that one message only: the client reconnects, and each channel on the socket hears a `1009` error.

## Connection options

Every channel and push subscription of one caller on one URL shares a socket. The caller's `ws` option sets that socket up, in `createCaller`, `createProxyCaller`, `createQueryCaller` and `createProxyQueryCaller` alike:

```ts title="lib/client.ts"
import { createProxyCaller } from "@noverax/courier"
import { routes } from "@noverax/courier/routes"

export const client = createProxyCaller(routes.api, {
  ws: {
    auth: async () => ({ token: await session.accessToken() }),
    backoff: { initialMs: 500, maxMs: 10_000 },
    messageQueue: { maxCount: 100, overflow: "drop-oldest" },
  },
})
```

- `auth` — what the client tells the server about itself, as socket.io's `auth` does: an object, or a function that returns one, called anew before every connect and reconnect so the token in it is current. It is sent in the socket's first frame, never in its URL, where proxies and servers log it, and the server's `onConnect` reads it as `auth` — see [Who a connection is](#who-a-connection-is). It is sent again, asked for anew, when the server asks with `connections.requireAuth`; a caller without it leaves that request unanswered, and the server closes the connection at its deadline. What JSON cannot carry — a `BigInt`, as an ORM gives a bigint column, an object that points back at itself — ends the connection with a `ConnectionError` that says so, as no attempt could send it.
- `backoff` — the wait before each reconnect: `initialMs` (1 s), `maxMs` (30 s), `factor` (2), `jitter` (on). See [Staying connected](#staying-connected).
- `messageQueue` — what the socket keeps to send while it cannot: messages sent while it reconnects, and those sent on a channel the server has not confirmed yet. `maxCount` (100) and `maxBytes` (1 MB) hold for all its channels together. `overflow` says what a message that finds no room does: with `"reject"`, the default, it is dropped with a warning and its `send` answers `false`; with `"drop-oldest"`, it is kept, and the oldest message waiting goes instead — its channel hears a `4429` error.
- `reconnectOnResume` — whether the page's signals act on the socket, `true` unless set to `false`. See [Staying connected](#staying-connected).
- `protocols` — WebSocket sub-protocols for the handshake.

How often the server pings the socket and the largest message it takes are the server's to say: it names both when it admits the socket, and the client goes by them — see [Staying connected](#staying-connected) and [Message size](#message-size).

A caller with `ws` options opens a socket of its own, beside the one another caller uses on the same URL, so its options are never dropped in favour of the other's.

## Staying connected

A socket is `connected` once the server has admitted it — `onConnect` accepted its credentials, and the server answered them with `auth_ok` — not as soon as it opens, so a connection the server refuses never reads `connected`. A server that answers in frames of another version of the protocol, as a replica of an older build does while a rollout replaces it, is left at once and called back after a wait.

A connection that drops reconnects on its own, and its channels subscribe again:

- **After a wait.** Each wait is drawn at random between 0 and `initialMs × factor^n`, `n` the attempts that failed in a row before it, and is never longer than `maxMs`, so clients that lost a server together do not come back to it together. A connection that stays open for 10 s counts as having worked: its next drop starts the waits over. A server that asks for a wait — one shutting down, one at capacity — is not called back sooner. With `jitter: false` every wait is the exponential one.
- **At once, when the page says so.** The network comes back (`online`, then a wait of up to a second at random), the page is shown again, it comes back from the back/forward cache, or its window gets focus. A wait the server asked for is kept all the same: the connection comes back up to a second at random after it, and its failed attempts stay counted, as the server's answer has not changed. A connection open at that moment is checked instead: it sends a ping, and a socket that does not answer within 5 s is taken for gone. `reconnectOnResume: false` turns this off. Node and React Native give no such signals: call `reconnect()` there, as from React Native's `AppState` when the app comes back to the foreground.
- **A socket that falls silent** — no frame for the server's ping interval and pong timeout together, as the server named them when it admitted the socket: 35 s for a Courier server's defaults — is taken for gone though it still reads as open: a network that dropped without a word sends no close.

In a React Native app, the app coming back to the foreground is the signal to pass on:

```ts title="app/realtime.ts"
import { AppState } from "react-native"

const room = client.chat.room({ room: "general", nick: "ada" })

AppState.addEventListener("change", (state) => {
  if (state === "active") room.reconnect()
})
```

A socket that takes longer than 15 s to open, or a server that takes longer than 15 s to admit it, counts as a failed attempt. A Courier server says why it closes a socket in a frame right before the close, and the client goes by that frame's code and wait: a balancer may lose the close itself, but not the frame before it. Some closes are not reconnected, as reconnecting would meet the same answer:

| Code | Why | The client |
| --- | --- | --- |
| `1000` | the server ended the connection | ends its channels as finished |
| `4401` | credentials refused, expired or not renewed in time | asks for its credentials anew, once, and signs in with them if they changed; otherwise ends its channels with an `AuthError` |
| `4403`, `4421` | origin or host not allowed | ends its channels with the error |
| `4409` | replaced by a newer connection of the same user | ends its channels: reconnecting would replace that one in turn |
| `4429` | too many connections from the address or the user, or too much sent before the connection was let in | called back after the wait the server names, 10 s for too many connections, as a place may free meanwhile; with none named, as for too much sent, ends its channels with a `RateLimitError` |
| `1002` | the two ends speak different versions of the protocol | from a server older than the client, reconnects after a wait, as a rollout replaces that server; from a newer one, ends its channels with the error — the page needs loading again |
| `1003`, `1007`, `1008`, `4000`–`4099` | data or a policy the server will not take, or the application said no | ends its channels with the error |
| `4400`–`4499`, those above and `4408` aside | a refusal of what the client sent, as an HTTP `4xx` is: a frame the protocol does not take (`4400`), what the connection names is not there (`4404`), too much (`4413`), what its schema refuses (`4422`) — and so a `RealtimeError` of such a code that `onConnect` throws | ends its channels with the error, as a stream ends on a `4xx` |

Every other close — a dropped network (`1006`), a server going away (`1001`, `1012`), an internal error (`1011`), a slow consumer (`1013`), a timeout (`4408`) — reconnects, no sooner than the wait the server named, if it named one.

A stream reconnects on the same rules, with what an HTTP stream has in place of a socket's, from the `Last-Event-ID` of the last event it read:

- Its waits are drawn as a socket's are, and start over once a stream stayed open 10 s, so a server that ends each stream at once is called back less and less often. A server that asks for a wait — the stream's `retry:` field, `Retry-After` on a `429` or a `503` — is not called back sooner, nor waited for longer than five minutes.
- An attempt has the 15 s a socket has to open, from asking `beforeConnect` for what it opens with to the server's answer: a balancer that took the request and never answers, or a refusal whose body never ends, counts as a failed attempt. What a refusal says is read from its first 64 KiB; a longer one says its status text.
- A line or an event longer than 1 MiB of text ends the stream with a `ConnectionError` of code `1009`, as a socket's message too large is told: a server that never ends one would hold the client's memory for as long as it sends, and reconnecting would read the same event again. Data larger than that goes in several events.
- A `401` is tried once more, at once, when the credentials asked for anew have changed — a session renewed meanwhile; the same credentials, or a second `401`, end the stream with an `AuthError`. Any other refusal from `400` to `499`, `408` and `429` aside, ends it with its error.
- The page's signals bring back a stream that waits to reconnect, once a wait its server asked for is over, as a socket's. A stream has no ping to be checked with, and a Courier server comments on it every 25 s: one open when a signal comes is opened again only if it has heard nothing for longer than its `heartbeatTimeout`, 45 s, as after the computer slept. A stream that hears nothing for that long while the page is in use is opened again too.

`subscribeSSE` from `@noverax/courier/realtime` takes `backoff`, `heartbeatTimeout`, `maxAttempts` and `reconnectOnResume` for a stream opened directly; a caller's streams keep these defaults.

## Who a connection is

A browser's WebSocket carries the page's cookies on its handshake, and nothing else: no script can put an `Authorization` or an API key on it, and a token put in the URL ends up in the logs of every proxy and server it passes. So a Courier client says who it is in a frame of its own, the first it sends on every socket — before its subscriptions, on every reconnect too:

- its `ws.auth`, which the server's `onConnect` reads as `auth`;
- the headers it could not put on the handshake, which the server reads as the handshake's own: `onConnect`'s `request` carries them, and so does every subscription's middleware and session. A header the handshake has keeps its value, and none a browser or a proxy sets itself — `Cookie`, `Origin`, `Host`, the `Sec-` and forwarding headers — is taken from the frame.

Those headers are the ones the caller's calls send: the API's `headers`, the caller's `headers`, and the user's [session](/docs/server-side/session#streams-and-channels) — its bearer token, and on a server its cookies and `forward`'s headers. Where the platform's WebSocket takes headers on its handshake — on a server, in a React Native app — they go there instead, and the frame carries `auth` alone.

```ts title="server.ts"
const server = await createCourierServer({
  sources,
  onConnect: async ({ request, auth }) => {
    const user = await users.byToken(auth?.token ?? bearerOf(request))
    if (!user) throw new Error("Unauthorized")
    return { userId: user.id }
  },
})
```

The server holds what a client sends until `onConnect` has admitted its connection, then handles it in order, so a subscription made as the socket opens is not lost while the user is looked up. What it holds is bounded: twice `maxSubscriptionsPerConnection` frames, four times `maxMessageSize` in all, and no frame larger than `maxMessageSize`. A socket that sends more before it is admitted is closed with `4429`, naming no wait: a Courier client does not come back after it. A socket whose first frame is no `auth` of the protocol's version — a client that is not Courier's, or a page left open from an older build — is refused with `1002` and why, and one that sends nothing for `authTimeoutMs` (3 s) is closed with `4408`.

To have a client prove who it is again on an open connection — its token about to expire — call `connections.requireAuth(connectionId, { timeoutMs })`, or name every connection of a user with a selector, `connections.requireAuth({ meta: { userId } })`, which reaches them on every replica that shares the pub/sub adapter: the client sends its credentials again, asked for anew, and `onReauth` reads them as `onConnect` does and returns the connection's new metadata.

Credentials `onReauth` refuses close the connection at once with `4401` — and so do any the client sends again to a handler with no `onReauth`, since nothing could check them; none sent by the deadline close it too. A request without a `timeoutMs` of its own gives the client the handler's `authRequiredTimeoutMs`, 30 seconds by default. A later request's deadline replaces an earlier one's, and `timeoutMs: 0` asks with none, which lifts it. Once renewed credentials change who the connection is, each of its subscriptions is authorized again, and one the new identity may not hold ends with `4403`. A `RealtimeError` thrown by `onConnect` — `ForbiddenError("Banned")` — closes the connection with its own code and message, and the client goes by that code as the table under [Staying connected](#staying-connected) says: one from `4400` to `4499` but `4401`, `4408` and `4429` ends its channels with the error. Anything else closes it with `4401` "Connection rejected", and the client goes on as after any `4401`: it asks once more, and signs in again only with credentials that changed.

`connections.disconnect(selector, { code, reason })` closes the connections a selector names — a connection id, `{ id: [...] }`, or `{ meta: { userId } }` — on every replica; see [A User's Connections, on Every Replica](/docs/deployment/replication#a-users-connections-on-every-replica).
