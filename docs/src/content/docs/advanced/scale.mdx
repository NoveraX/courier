## The project they are measured on

Every night Courier writes a project the size of a large company's and measures everything it runs on it. The project is the same every time, generated from a fixed seed:

| Part | What it holds |
| --- | --- |
| APIs | 5 sources, 1000 endpoints: 970 HTTP endpoints in 169 groups, a group inside every fourth one, 25 streams and 5 channels |
| Schemas | each group's records, input and patch in zod, with nested objects, arrays, unions and a discriminated union |
| Code | 1420 files: 600 server modules calling the APIs directly and 100 pages calling them through the app's proxy — 3300 call sites — and 39 internal libraries that import each other |
| Courier | `courier.config.ts`, the app's server with `createCourierServer`, the endpoints its pages call marked `.expose()` and `courier.routes.ts` written from the marks, and `courier.mocks.ts` with a mock for each API, 200 records a collection |

The figures below were measured on an Apple M2 Max laptop with Node 24. The nightly job runs on a CI runner two to four times slower, so a figure that follows the machine's speed is held to the same work done without Courier, measured in the same run: the mocks to bare Node servers answering the same requests, the app's server to the same calls made straight to the backend, a large answer to the same answer fetched and checked by the same schema. Every other time has a budget twice what the CI runner takes. Either way a budget catches a change that makes Courier markedly slower or heavier, not a slower machine.

| Measured | Figure |

| Importing the project's OpenAPI document — 970 operations, 941 KB — in Studio | read in 42 ms, 341 files of code written in 186 ms; `tsc` over them 2.5 s, no errors |

### Large answers

An endpoint answering a list read through its zod schema, with Studio attached and without. Studio is sent at most 16 KB of any body — the first items of a list, a part of each large field — whatever its size; it asks the app for the whole one when you open it.

| Answer | Fetched and checked by the schema, without Courier | Through Courier, without Studio | With Studio attached | Sent to Studio |
| --- | --- | --- | --- | --- |
| 1,000 records, 0.3 MB | 1.8 ms | 1.8 ms | 3.2 ms | 18 KB |
| 10,000 records, 3.5 MB | 16 ms | 15 ms | 27 ms | 18 KB |
| 50,000 records, 17.6 MB | 87 ms | 92 ms | 155 ms | 18 KB |

### Studio and its mocks

| Measured | Figure |
| --- | --- |
| Studio answering, from its start | 1.6 s on a project it has never loaded, 0.9 s after |
| The five mocks listening, from Studio's start | 2.2 s |
| Memory while they start | 1.4 GB, for about ten seconds |
| Memory at rest — Studio and five mock processes | 640 MB: Studio about 180 MB, each mock 110–140 MB |
| Processor at rest | 0.5 % of one core |
| The mocks under 32 concurrent connections | 8,500 requests a second, 3.3 ms at the median, 15 ms at p99, none failed |
| The same requests answered by bare Node servers, for comparison | 29,500 requests a second, 0.9 ms at the median, 4.2 ms at p99 |
| Processor time a request, Studio's recording of it included | 0.29 ms, against 0.05 ms for a bare Node server |

Each mock runs in a process of its own, so one that crashes or hangs leaves the others serving, and the mocks share the machine's cores under load. Each process holds Node itself and everything `courier.mocks.ts` loads — every API's definitions, the seeded records — which is what most of its memory is.

### The app's server with Studio attached

The app's own server — Courier's proxy in front of the five APIs, with its middleware and response schemas — called by its pages, 32 calls at a time:

| | Calls a second | Median | p99 |
| --- | --- | --- | --- |
| Straight to the backend, for comparison | 9,600 | 2.8 ms | 9.8 ms |
| Through the app's server | 6,100 | 4.9 ms | 9.7 ms |
| Through the app's server, attached to Studio | 3,700 | 8.2 ms | 14.6 ms |

A server attached to Studio reports some seventeen events for each call it serves — the call's start and end, each middleware, each validation, the fetch, the answer's shape — and sends them in batches: every event of one turn of its event loop leaves together, in one message, once the turn is over. Only development servers attach; in production nothing is reported.

## Running them yourself

The measurements are a script of the repository. It writes the project to the system's temp folder, starts Studio, its mocks, the app's server, Chromium and VS Code, measures them, and stops each one. It prints a line a figure with its budget, and exits with 1 when one is over:

```bash
npm run test:scale
```

A larger company, some of the steps alone, or the report as JSON:

```bash
node scripts/scale/run.mjs --endpoints 3000 --only tsc,runtime,studio,proxy --json scale-report.json
```

The steps are `tsc`, `runtime`, `codegen`, `payloads`, `studio`, and inside it `proxy`, `editor`, `extension`, `mocks` and `ui`. Studio listens on port 7401, its mocks from 7410, the bare servers they are held to from 7420, the app on 7400; `--ports` moves all of them.

## On a project of your own of this size

- **Offer agents what they need.** The project marks every endpoint for agents, which makes 970 tools and 2 MB of their descriptions — far past the 40 where some clients start leaving tools out. The MCP server lists them in 30 ms; what to offer is [the project's agents policy](/docs/agents/overview#what-agents-may-call).
- **Studio keeps the latest 2000 requests** and sends a page that opens as many of them as fit 16 MB. Clear the log from the Timeline to start afresh.
- **Each mock is a process of its own.** One you do not need running still takes its memory; stop it from the Mocks page.
- **A mock's records reach the page that shows them.** A page is told each collection's count as it opens; the Mocks section asks Studio for the records of the mock it shows, from the moment its link is pointed at, and keeps them current from then on. A page that never opens it is never sent them.
- **Transforms are kept in `node_modules/.cache/courier`.** Studio, an attached app, the MCP server and `courier-server` reuse each module's transform until its bytes change, so only the first start pays for them; `COURIER_TRANSFORM_CACHE=0` turns that off.
