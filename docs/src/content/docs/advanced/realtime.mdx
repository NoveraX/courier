## Overview

A `stream` delivers server-sent events; a `channel` is a WebSocket subscription, which the caller can also send on when it names `.send()`. Either one is served by the process that defines it with `.implement()`, or describes where another process serves it with `.get()`, `.connect()` or `.via()`.

```ts title="api/chat.ts"
import { courier, defineGroup } from "@noverax/courier/define"
import { z } from "zod"

const { channel } = courier()

export const chat = defineGroup({
  prefix: "chat",
  endpoints: {
    room: channel
      .variables(z.object({ room: z.string(), nick: z.string() }))
      .topic((v) => ({ room: v.room }))
      .send(z.object({ text: z.string() }))
      .response(z.object({ from: z.string(), text: z.string() }))
      .implement((v) => ({
        onJoin(ctx) {
          ctx.send({ from: "server", text: `welcome to ${v.room}` })
        },
        onMessage(ctx, message) {
          ctx.broadcast(ctx.topic, { from: v.nick, text: message.text })
        },
      })),
  },
})
```

## Serving a stream

A stream's `.implement()` takes an async generator, handed the subscription's `variables`, a `signal` that aborts when the client leaves, the `lastEventId` a reconnecting client resumes after, and the request's `headers`. Each event it yields is `{ data }`, with an `event` name or an `id` where it needs them; `tracked(id, data)` gives the event an id, so a client that reconnects is handed only what it missed:

```ts title="api/orders.ts"
import { courier, defineGroup } from "@noverax/courier/define"
import { ForbiddenError } from "@noverax/courier"
import { tracked } from "@noverax/courier/realtime"
import { z } from "zod"

const { stream, channel } = courier()

export const orders = defineGroup({
  prefix: "orders",
  endpoints: {
    updates: stream
      .variables(z.object({ shop: z.string() }))
      .response(z.object({ id: z.string(), state: z.string() }))
      .implement(async function* (ctx) {
        if (!(await canWatch(ctx.headers, ctx.variables.shop))) {
          throw new ForbiddenError("Not a member of this shop")
        }
        for await (const order of orderChanges(ctx.variables.shop, ctx.lastEventId, ctx.signal)) {
          yield tracked(order.id, order)
        }
      }),
    // A channel nobody sends on is served the same way; it yields the values themselves
    ticker: channel.response(z.number()).implement(async function* () {
      yield 1
    }),
  },
})
```

Returning ends the stream: the client stops reading and does not reconnect. Throwing fails it. A `RealtimeError` — `ForbiddenError`, `AuthError`, `RateLimitError`, `TimeoutError`, or one built with its own code — reaches the client with its code and message; any other error reaches it as code `5000`, "Stream failed", and in full only the server's log.

## Reaching a stream or a channel

A stream or channel served with `.implement()` is reached through the server that serves it — the proxy routes of your framework adapter, or a [standalone server](/docs/deployment/standalone-server) — so a proxy caller opens it: `createProxyCaller`, or `createProxyQueryCaller` for the React hooks.

A direct caller, `createCaller` or `createQueryCaller`, sends everything to the API's `baseURL`, which is the upstream's address. Nothing serves this process's streams and channels there, so calling one through a direct caller throws `ConfigurationError("DIRECT_CALL_TO_SERVED_ENDPOINT")`, naming it, when it is called — the React hooks report it through `error` — and the rest of the API stays callable. A stream or channel addressed with `.get()`, `.connect()` or `.via()` is another process's, and a direct caller opens it at `baseURL`.

A proxy caller reaches another process's stream or channel too: the proxy relays it, opening it where its definition says. A stream is opened with the source's `headers`, the request headers the proxy lets through, and whatever the source's middleware sets. A browser reaches a third party's stream through its own server, with no CORS to configure and no key of its own to hold. A channel is subscribed to as a direct caller in the server's process would subscribe to it. The proxy relays the streams and channels it would forward as endpoints: one a `defineBoundary` leaves out stays unreachable.

- A stream's events pass on as they came: ids, event names, and data that is not JSON as its text. A dropped upstream connection is reopened from the last event id, while the client's stays open. The client's `Last-Event-ID` is sent upstream when it resumes.
- The stream ends as the upstream's ends. It fails as the upstream's fails: a refusal carries the upstream's status as code `4000 + status`, so a `401` arrives as `4401`. A client that leaves closes the upstream stream.
- A channel's frames pass both ways, and it ends as its upstream subscription ends, with its code — a connection the upstream refuses included. A message the upstream subscription has no room to hold, while it joins or comes back, is answered with a `4429` error on the channel, which goes on. Subscribers of the server with equal variables share one upstream subscription.
- A path parameter that is empty, `.` or `..` is refused before anything is sent, as it is for an HTTP call. Otherwise it would reach a route above the declared one with the server's credentials.

## How a subscription ends

A subscription ends in one of three ways, and the client can tell them apart.

- **The client closes it** — `close()`, or a React hook unmounting. Nothing is reported.
- **The server finishes it** — a stream's generator returned, or a channel closed itself. Iterating a stream ends (`for await` leaves its loop); a channel's status becomes `disconnected`. Neither reconnects.
- **The server fails it** — the handler threw, the subscription or the join was refused, its variables failed their schema, or a limit was reached. Iterating a stream rejects with a `RealtimeError` carrying the code and message the server sent; a channel emits it on `error`, then its status becomes `disconnected`. A refusal answered with an HTTP status arrives as code `4000 + status`, so a `401` is `4401`.

A dropped connection is none of these: the client reconnects, resumes a stream after the last event id it saw, and subscribes its channels again. When it has spent its retries, iterating the stream rejects with a `ConnectionError`.

```ts
import { isRealtimeError } from "@noverax/courier"

const updates = client.orders.updates({ shop: "north" })
try {
  for await (const event of updates) render(event.data)
  // the server finished the stream
} catch (error) {
  if (isRealtimeError(error) && error.code === 4403) showNoAccess(error.message)
  else throw error
}

const room = client.chat.room({ room: "general", nick: "ada" })
room.on("error", (error) => notify(error.message)) // a refused message: the channel goes on
room.on("status", (status) => setOnline(status === "connected"))
```

A channel's `error` event also reports what it refused without ending: a message that failed its schema (`4422`), one larger than the server accepts (`4413`), or an `onMessage` that threw. `send()` returns whether the message went out or waits for the channel; `false` means it was dropped, with a warning.

## Topics

Every subscription to a channel is on a topic: the endpoint, `source.group.method`, qualified by a key. `ctx.topic` is the subscriber's own, and `ctx.broadcast(topic, data)` sends to every other subscriber on it — every replica's, with a [`pubsub` adapter](/docs/deployment/redis).

Without `.topic()`, the key is all of a subscriber's variables: subscribers share a topic only when their variables are equal. That is the safe default for a feed whose variables pick what it shows, but it splits a room into as many topics as it has members as soon as a variable belongs to one member — a nickname, a cursor colour.

`.topic()` names what subscribers share a topic by. It reads the variables as the schema produced them, and returns what JSON can carry. In the channel above, everyone in room `r1` is on one topic, so a broadcast reaches all of them, while each keeps its own `nick` in `v` and `ctx.variables`. A key that throws ends that subscription with code `5000`.

On one connection, subscriptions whose key is equal are one subscription: the newer subscribe replaces the older, whose `onLeave` runs, and both of the client's channels receive what is sent on the topic. Two browsers, or two tabs, are two connections.

`.topic()` is named before `.implement()`. A channel another process serves has its topics decided there, so naming it before `.connect()` or `.via()` throws `ConfigurationError("TOPIC_ON_REMOTE_CHANNEL")`.

<Callout variant="info" title="How a topic reads">
  The key is canonical JSON — `api.chat.room#{"room":"r1"}` — so every distinct key is a topic of its own. `qualifyTopic` from `@noverax/courier/realtime` builds a topic for `broadcastToTopic` on the server's connection registry.
</Callout>

## What a channel sends

A stream's events, a push channel's values and what a channel's handlers pass to `ctx.send()` and `ctx.broadcast()` are held to the endpoint's `.response()` schema before they leave the server, and the client receives the schema's output — defaults filled in, transforms applied. A channel's `ctx.send()` or `ctx.broadcast()` of a value that does not match throws a `RealtimeValidationError` where it was called and sends nothing; a channel's response schema must validate synchronously. [Validation](/docs/validation/standard-schema#channels) has the details.

## Message size

A server accepts messages up to its `maxMessageSize`, 64 KB by default, and answers a larger one with a `4413` error on a connection that stays open. The client does not send one: a channel's `send` of a message whose encoded frame is longer than its own `maxMessageSize` — 64 KB unless the caller's `ws` says otherwise — puts nothing on the wire: `send` answers `false`, and the channel's `error` event reads code `4413`. The channel and everything else on the socket go on.

A server whose WebSocket layer closes the socket over a frame too large to read, with close code `1009`, loses that one message only: the client reconnects, and each channel on the socket hears a `1009` error.

## Connection options

Every channel and push subscription of one caller on one URL shares a socket. The caller's `ws` option sets that socket up, in `createCaller`, `createProxyCaller`, `createQueryCaller` and `createProxyQueryCaller` alike:

```ts title="lib/client.ts"
import { createProxyCaller } from "@noverax/courier"
import type { api } from "@/api"
import { boundary } from "./boundary"

export const client = createProxyCaller<typeof api>("api", {
  boundary,
  ws: {
    getAuthToken: () => session.accessToken(),
    backoff: { initialMs: 500, maxMs: 10_000 },
    heartbeat: { intervalMs: 25_000, timeoutMs: 10_000 },
    maxMessageSize: 65_536,
  },
})
```

- `getAuthToken` — a token sent as `?token=` on every connect and reconnect, and sent again, on the open socket, when the server asks for a fresh one with `sendAuthRequired`. Without it the server's request goes unanswered, and the server closes the connection at its deadline — as it does when the server has no `onTokenRefresh` to check the token.
- `backoff` — the delay before each reconnect: `initialMs` (1 s), `maxMs` (30 s), `factor` (2), `jitter` (on).
- `heartbeat` — the server's ping interval and pong timeout; a server silent for longer than the two together is taken for gone, and the client reconnects.
- `messageQueue` — how much is kept to send while reconnecting: `maxCount` (100) and `maxBytes` (1 MB). A message beyond it is dropped with a warning, and its `send` answers `false`.
- `protocols` — WebSocket sub-protocols for the handshake.
- `maxMessageSize` — the largest message sent; see [Message size](#message-size).

A caller with `ws` options opens a socket of its own, beside the one another caller uses on the same URL, so its options are never dropped in favour of the other's.
